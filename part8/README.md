# part8 — 極限と余極限。JOIN は引き戻しで、GROUP BY は余等化子

第2回で積と余積を見ました。その一般化が**極限**と**余極限**です。有限極限は「積 + イコライザ」に分解でき、その具体形のひとつが**引き戻し（pullback）**。集合の圏では、これは INNER JOIN そのものになります。

```
Pullback(f, g) = { (a, b) | f(a) = g(b) }
```

`f` を「a の結合キー」、`g` を「b の結合キー」と読めば、そのまま `JOIN ... ON a.k = b.k` です。

## 動かす

```bash
go test -v ./part8/
go test -bench=. -benchmem -run='^$' ./part8/
```

## 何を確認すればいいか

### 1. 作り方が違っても、できる対象は同じ

```bash
go test -v -run 'Agree|Universal|Decomposes' ./part8/
```

引き戻しを3通りで作ります。定義どおりの総当たり、ハッシュで索引する版、「積を作ってからイコライザで絞る」版。**極限は同型を除いて一意**なので、3つとも同じものになるはずです。`TestAllPullbackConstructionsAgree` が確認します。

`TestPullbackUniversalProperty` は普遍性そのものを検査します。$f \circ p = g \circ q$ を満たす任意の錐 $(Z, p, q)$ から引き戻しへの媒介射がちょうど1つ存在すること。

### 2. 同じ対象でも、作り方でコストは桁が変わる

```bash
go test -bench=PullbackConstruction -benchmem -run='^$' ./part8/
```

n=1,000 での比較です。

| 方式 | ns/op | B/op | allocs/op |
|---|---:|---:|---:|
| 定義どおり（総当たり） | 3,271,597 | 685,297 | 19 |
| ハッシュで索引 | **116,027** | 788,323 | 492 |
| 積を作ってイコライザ | 3,819,715 | **16,692,467** | 20 |

**ハッシュ版は 28.2倍速い。ただしメモリでは損をしています**——確保したバイト数は 1.15倍、確保回数は 25.9倍。索引の `map` を作るぶんです。「速いほうがメモリも得」ではありません。

積を実体化する版は、$n^2$ の組を全部置くのでメモリが **24.4倍**。定義に忠実であることと、実装として妥当であることは別です。

### 3. 結合の順序を変えても答えは同じ。コストは 133倍違う

```bash
go test -bench=JoinOrder -benchmem -run='^$' -v ./part8/
```

引き戻しの補題（pullback lemma）を実務の言葉に直すと「**結合の順序を入れ替えても同じ答えになる**」です。`TestJoinOrdersAgree` が property-based に確認します。

そのうえで測ります。User 4,000件・Assignment 4,000件（dept は10種類）・ActiveProject 5件。

| 順序 | 中間データ | ns/op | B/op |
|---|---:|---:|---:|
| (User ⋈ Assignment) ⋈ Active | **1,600,146** | 31,725,447 | 315,192,386 |
| User ⋈ (Assignment ⋈ Active) | **9** | **237,666** | **675,683** |

**時間 133倍、確保量 466倍。** dept が10種類しかないので User ⋈ Assignment は $4000 \times 4000 / 10$ まで膨らみ、active な project は5件しかないので Assignment ⋈ Active は9件まで縮みます。

**圏論が保証するのは「同じ答えになる」ところまで**です。どちらの順で計算するかは、キーの分布——圏論の外側——が決めます。クエリプランナがやっているのは、まさにこの選択です。

### 4. 極限と余極限は入れ替えてよいとは限らない

```bash
go test -v -run 'Commute|Pushdown' ./part8/
```

集約（GROUP BY）は余極限の側です。同じキーの行を**同一視する**操作、つまり余等化子にあたります。

極限どうし（JOIN と JOIN）は入れ替えてよい。上でそれを使いました。では**極限（filter）と余極限（GROUP BY）**はどうか。

述語がキーだけを見ているなら、入れ替えられます。

```bash
go test -bench=FilterPushdown -benchmem -run='^$' ./part8/
```

| 順序 | ns/op | B/op |
|---|---:|---:|
| 集約してから絞る | 1,935,042 | 179,960 |
| 絞ってから集約する | **936,084** | 159,096 |

**2.07倍。** 200,000行を先に絞れば、集約する行が減るぶん得です。

**述語が集約の結果を見ているなら、入れ替えられません。**

```
HAVING SUM(v) > 10  →  [a:12:3  b:20:1]
WHERE  v > 10       →  [b:20:1]
```

`a` は 4 が3行で合計12なので `HAVING` では残りますが、**個々の行はどれも10以下**なので `WHERE` では全部落ちます。無作為な500ケースで数えると、**413ケース（82.6%）で答えが変わりました**。キーだけを見る述語のほうは 500/500 で一致します。

**「filter は早いほうがいい」は、述語が何を見ているかを確かめてから言うこと。**
