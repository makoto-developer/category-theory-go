# part7 — レンズ則は Go では足りない

レンズ（Lens）は「大きい構造 S の中の小さい部分 A」への焦点を、`Get` と `Set` の組で表したものです。合成できるので、入れ子の奥まで届きます。

```go
type Lens[S, A any] struct {
	Get func(S) A
	Set func(S, A) S
}
```

レンズには**3つの法則**があります。

- **get-set**: 取り出してそのまま戻せば、元と同じ（`Set(s, Get(s)) == s`）
- **set-get**: 入れたものが取り出せる（`Get(Set(s, a)) == a`）
- **set-set**: 二度入れたら後勝ち（`Set(Set(s, a), b) == Set(s, b)`）

この3つを満たすものだけがレンズを名乗れます。**では、3つを満たせば安全なのか。**

## 動かす

```bash
go test -v ./part7/
go test -bench=. -benchmem -run='^$' ./part7/
```

## 何を確認すればいいか

### 1. 3則を全部通るレンズが、元の値を書き換える

```bash
go test -v -run 'Aliasing|Independent|Leaks' ./part7/
```

Go の struct は代入でコピーされます。**ただしその中の slice と map はコピーされません**。ヘッダだけがコピーされて、指している先は共有されたままです。

だから「素直に書いた」レンズはこうなります。

```go
Get: func(p Profile) []string { return p.Tags },
Set: func(p Profile, ts []string) Profile { p.Tags = ts; return p },
```

`TestAliasingLensStillObeysAllThreeLaws` が、**これが3則を全部通る**ことを property-based test で示します（100ケース）。値としての等しさで判定するかぎり、共有していることは見えません。

見えないだけで、壊れています。

- `TestAliasingLensBreaksIndependence` — `Get` の戻り値を書き換えると、元の `Account` が変わる
- `TestAliasingLensLeaksThroughSet` — `Set` に渡したスライスを後から書き換えると、格納先が変わる
- `TestModifyLeaksWhenTheFunctionMutates` — `Modify` に渡した関数の `append` が元を書き換える

**3則には「非破壊である」ことが入っていません。** 4つ目の性質——`Get` の戻り値を書き換えても元が変わらないこと——を別に検査する必要があります。

> 第3回で「法則は最適化の許可証だ」と書きました。裏を返すと、**法則が言っていないことは許可されていない**のではなく、**保証されていない**だけです。発展編1本目では法則がコストを保存しないことを見ました。今回は法則がエイリアスを検出しないことを見ています。

### 2. 法則を守ると、合成の深さぶん複製が重なる

```bash
go test -bench=LensDepth -benchmem -run='^$' ./part7/
```

エイリアスを避けるには、`Get` でも `Set` でも複製するしかありません。すると**合成したときに、同じデータが何度も複製されます**。

`Compose` の `Set` はこの形です。

```go
Set: func(s S, b B) S { return outer.Set(s, inner.Set(outer.Get(s), b)) }
```

`inner.Set` が複製し、そのあと `outer.Set` がもう一度複製します。段が増えれば、増えた数だけ重なります。

4,096要素のスライスを持つ構造で、合成の深さを振りました。

| 深さ | ns/op | B/op | allocs/op |
|---:|---:|---:|---:|
| 1 | 14,010 | 131,104 | 3 |
| 2 | 20,774 | 196,672 | 5 |
| 3 | 27,840 | 262,240 | 7 |
| 4 | 33,918 | **327,808** | 9 |

**1段ごとに 65,568 バイトちょうど増えます。** これは 4,096要素の `[]string` の複製1回ぶん（4096 × 16 + スライスの分）です。確保回数も1段につき2回ずつ増えます。

**深さに比例してコピーが増える**わけです。設定構造体の5段奥にレンズを通したら、ペイロードを5回コピーします。手書きなら1回で済みます。

### 3. 参照型を通らなくても、合成そのものに代金がある

```bash
go test -bench=UpdateEmail -benchmem -run='^$' ./part7/
```

`Account.Profile.Contact.Email` を差し替えるだけ——参照型を1つも通らない経路です。

| 方式 | ns/op | allocs/op |
|---|---:|---:|
| レンズ3枚を合成 | 40.46 | 0 |
| 手書き | **2.950** | 0 |

**13.7倍**です。アロケーションはどちらもゼロなので、差は関数値の間接呼び出しだけ。3枚合成すると `Set` の経路に `Get` 2回と `Set` 3回が並びます。

### 4. 全部並べる

```bash
go test -bench=UpdateTags -benchmem -run='^$' ./part7/
```

4,096要素の `Tags` を差し替える（`Meta` は8要素）。

| 方式 | ns/op | B/op | allocs/op | 非破壊か |
|---|---:|---:|---:|---|
| レンズ（法則を守る） | 16,163 | 131,408 | 4 | ✅ |
| レンズ（素直に書いた） | **25.98** | 0 | 0 | ❌ |
| 手書き（複製する） | 7,876 | 65,872 | 3 | ✅ |
| 手書き（素直に書いた） | **3.206** | 0 | 0 | ❌ |

**622倍**の開きがあります。そして注目すべきは**法則を守る2つの比較**です。レンズ 16,163ns / 131,408B に対し、手書き 7,876ns / 65,872B。**ちょうど2倍**。上の2段合成ぶんの重複コピーがそのまま出ています。

素直に書いた版がサイズによらず 26ns で一定なのは、**何もコピーしていないから**です。速いのではなく、仕事をしていません。
