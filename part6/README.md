# part6 — 双対を取る。F余代数と unfold、そして融合は起きるのか

第3回で F代数と `fold`（catamorphism）を見ました。矢印を全部裏返すと **F余代数と `unfold`**（anamorphism）になります。`fold` が「畳んで壊す」なら `unfold` は「種から生やす」。

両者を繋いだものが **hylomorphism**（`unfold` してから `fold`）です。間に立つ構造は作られてすぐ畳まれるので、理屈のうえでは要りません（deforestation）。**Go で本当に消えるのか**を測ります。

## 動かす

```bash
go test -v ./part6/
go test -bench=. -benchmem -run='^$' ./part6/
```

## 何を確認すればいいか

### 1. 中間構造は、自動では消えない

```bash
go test -bench=Hylomorphism -benchmem -run='^$' ./part6/
```

1〜n の総和を、3通りの hylomorphism で計算します（n=100,000）。

| 方式 | ns/op | B/op | allocs/op | 要素あたり |
|---|---:|---:|---:|---:|
| 中間スライスを作る | 596,727 | **4,101,351** | 26 | 5.97 ns |
| 手で融合した | 148,764 | **16** | 1 | 1.49 ns |
| `iter.Seq` を挟む | 211,196 | 16 | 1 | 2.11 ns |
| 手書きループ | 27,296 | 0 | 0 | 0.27 ns |

**Go のコンパイラは deforestation をしません。** 素直に書くと 4.1MB の中間スライスが本当に確保されます。手で融合すると **16バイト・1アロケーション**まで落ち、**4.0倍**速くなります。

### 2. 融合後に残る代金は、Go のバージョンで変わる（ここが予想と逆）

上の表は go1.25.1 のものです。融合版は中間構造をゼロにしたのに**手書きループの 5.5倍**遅く、「融合してもタダにはならない」と結論しかけました。

バージョンを横断して測ると、話が変わります。[benchsweep](https://github.com/makoto-developer/benchsweep) で隔離環境（`cpus=4` / `cpuset=0-3` / `GOMAXPROCS=4`）に揃え、`-count=10` で測った n=100,000:

| | go1.25.13 | go1.26.5 |
|---|---:|---:|
| 融合版 ns/op | 122,938 | **40,060** |
| 融合版 allocs/op | **1** | **0** |
| 手書きループ ns/op | 24,798 | 32,734 |
| **融合版 ÷ 手書きループ** | **4.96倍** | **1.22倍** |
| `iter.Seq` 版 | 189,624 | 190,409（**1.00倍**） |

**Go 1.26 でクロージャの割り当てが消え（1 → 0）、融合版が 3.07倍速くなりました。** 手書きループとの差は 4.96倍から 1.22倍に縮み、測定範囲も重なります（融合版 36,107〜44,386 / 手書き 29,389〜40,165）。エスケープ解析がクロージャをスタックに載せたと見られます。

**一方 `iter.Seq` 版は 1.26 でも 1.00倍で、まったく改善していません。** 融合の代金は消えても、継続渡しの往復は消えません。

**「融合すればゼロコスト」も「融合しても代金は残る」も、バージョンを言わずに書けば誤りになります。**

### 3. 普通に書いたマージソートは、hylomorphism を手で融合したものだった

```bash
go test -bench=MergeSort -benchmem -run='^$' ./part6/
```

マージソートは教科書的な hylomorphism です。**分割の木を `unfold` で生やし、マージで `fold` する**。n=100,000 で測ります。

| 方式 | ns/op | B/op | allocs/op |
|---|---:|---:|---:|
| 木を作ってから畳む | 14,004,434 | 23,657,763 | 299,998 |
| 木を作らない（普通のマージソート） | 8,775,459 | 14,057,748 | 99,999 |
| `slices.Sort` | **5,243,436** | **0** | **0** |

木を作ると **1.60倍**遅く、アロケーションは **3.0倍**（$3n$ 対 $n$）。増えた $2n$ が `SplitTree` の節と葉です。

**普段書いているマージソートは、すでに融合済みの hylomorphism です。** 木を持たないのは最適化ではなく、そう書くのが自然だからで、圏論の言葉で見ると「何を省略していたか」が分かります。

### 4. 種が終了条件を持つと、呼び出し側からループが消える

```bash
go test -v -run 'Paginate' ./part6/
```

カーソル方式のページングは余代数そのものです。`Cursor` が「次があるか」を持つので、呼ぶ側に `for` も打ち切り判定も要りません。

**余代数は種だけを見る純粋な関数でなければなりません。** 終了フラグをクロージャに隠すと、同じ種で2回展開したときに壊れます。`TestPaginateCoalgebraIsPure` がそれを検査しています。

### 5. 遅延であること

```bash
go test -v -run 'StopOnBreak' ./part6/
```

`UnfoldSeq` は無限に続く余代数を渡しても止まります。`break` した時点で余代数の呼び出しも止まることを確認しています（3個取ったら呼び出しも3回）。
