# part6 — 双対を取る。F余代数と unfold、そして融合は起きるのか

第3回で F代数と `fold`（catamorphism）を見ました。矢印を全部裏返すと **F余代数と `unfold`**（anamorphism）になります。`fold` が「畳んで壊す」なら `unfold` は「種から生やす」。

正確には、catamorphism は始代数からの一意な射、anamorphism は終余代数への一意な射です。ここでの `Coalgebra[S,A]` は **リスト関手 $F(X) = 1 + A \times X$ の余代数** $S \to F(S)$ を Go で表したもので、`bool` が直和のタグにあたります。

両者を繋いだものが **hylomorphism**（`unfold` してから `fold`）です。間に立つ構造は作られてすぐ畳まれるので、理屈のうえでは要りません（deforestation）。**Go で本当に消えるのか**を測ります。

> ここの `Hylo*` は一般の関手に対する hylomorphism ではなく、リスト関手の anamorphism と**左畳み込み**（`step` が `func(B, A) B` なので `foldl` 型）を繋いだ限定版です。後半のマージソートは別の関手 $F(X) = \text{葉} + X \times X$ で、`SplitAna` / `MergeCata` を直接書いています。

## 動かす

```bash
go test -v ./part6/
go test -bench=. -benchmem -run='^$' ./part6/
```

## 何を確認すればいいか

### 1. 中間構造は、自動では消えない

```bash
go test -bench=Hylomorphism -benchmem -run='^$' ./part6/
```

1〜n の総和を hylomorphism で計算します（n=100,000・[benchsweep](https://github.com/makoto-developer/benchsweep) の隔離環境・`-count=10` の中央値）。

| 方式 | go1.25.13 ns/op | go1.26.5 ns/op | allocs/op |
|---|---:|---:|---:|
| 中間スライスを作る | 860,148 | 1,092,637 | 25 |
| 手で融合（余代数を変数で渡す） | 136,340 | 97,170 | 0 |
| 手で融合（余代数を呼び出し位置で組む） | 137,194 | **33,077** | 0 |
| `iter.Seq` を挟む | 189,208 | 191,165 | 0 |
| 手書きループ | 24,629 | 35,366 | 0 |

**Go のコンパイラは deforestation をしません。** 素直に書けば中間スライスが本当に確保されます（25 allocations・約 4.1MB）。手で融合すればゼロになります。

### 2. アロケーションが 0 になっても、速さは自動的にはついてこない

ここが予想と逆でした。融合したのだから速さも揃うだろう、と思っていました。

**Go 1.25 では、余代数をどう渡しても変わりません**（136,340 と 137,194）。手書きループの約 5.5倍が残ります。

**Go 1.26 では、余代数を呼び出し位置で組むと 33,077 ns まで落ち、手書きループ（35,366 ns）と同じになります。** 同じ 1.26 でも、余代数をいったん変数に入れると 97,170 ns で、3倍近く遅くなります。

つまり **「融合すればゼロコストになる」も「融合しても遅いままだ」も、バージョンと書き方を言わずに述べると誤りになります。**

> 原因は特定していません。観測できるのは「1.26 で、呼び出し位置に余代数を書いた場合だけ速くなる」ことまでです。コンパイラが余代数を見通して要素ごとの間接呼び出しを消したように見えますが、`-gcflags=-m` を 1.25 と 1.26 で比べても差は出ませんでした。断定するには逆アセンブルの比較が要ります。

**`iter.Seq` 版はどちらのバージョンでも変わりません**（189,208 と 191,165）。アロケーションは 0 でも手書きループの 5.4〜7.7倍かかります。要素ごとに `yield` を呼んで戻る往復が効いていそうですが、その往復だけを除いた対照を測っていないので切り分けられていません。

### 3. 普通に書いたマージソートは、hylomorphism を手で融合したものだった

```bash
go test -bench=MergeSort -benchmem -run='^$' ./part6/
```

マージソートは教科書的な hylomorphism です。**分割の木を `unfold` で生やし、マージで `fold` する**。n=100,000（go1.26.5）:

| 方式 | ns/op | allocs/op |
|---|---:|---:|
| 木を作ってから畳む | 13,023,388 | 299,998 |
| 木を作らない（普通のマージソート） | 9,050,680 | 99,999 |
| `slices.Clone` + `slices.Sort` | **4,989,742** | 1 |

木を作ると **1.44倍**遅く、アロケーションは **3.0倍**（$3n$ 対 $n$）。木の節が $2n-1$、マージの出力が $n-1$ で、合わせて約 $3n$ です。

**普段書いているマージソートは、すでに融合済みの hylomorphism です。**

> 比較条件について。`MergeSortHylo` と `MergeSortFused` は入力を破壊しません（`merge` が新しい出力を確保し、入力側はスライスヘッダを進めるだけ）。破壊的なのは `slices.Sort` だけなので、そちらにだけ `slices.Clone` を入れ、確保も計測に含めています。

### 4. 種が終了条件を持つと、呼び出し側からカーソル操作が消える

```bash
go test -v -run 'Paginate' ./part6/
```

カーソル方式のページングは余代数そのものです。`Cursor` が「次があるか」を持つので、呼ぶ側から**カーソルの更新と終了判定**が消えます（反復そのものは `for range` として残ります）。

進行状態をクロージャに隠さず種に入れておくと、同じ種から何度でも展開し直せます。`TestPaginateCanRestartFromSameSeed` がそれを検査しています。**これは「余代数が純粋である」ことの検査ではありません**——Go の型は純粋性を保証しませんし、`fetch` 自身は通信します。

### 5. 遅延であること

```bash
go test -v -run 'StopOnBreak' ./part6/
```

`UnfoldSeq` は無限に続く余代数を渡しても止まります。`break` した時点で余代数の呼び出しも止まります（3個取ったら呼び出しも3回）。
